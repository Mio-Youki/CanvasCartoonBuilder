## 发现途径

第 4 批真实编辑器性能夹具，输入 `karsten.jpg`＋半透明椭圆，Full 预览。640×360、采样格3时，工作面为214×120。

对照 CPU 与 GPU 的固定0.9s画面：阈值单卡静态有90个预乘通道差超过2，最大差200、最大Alpha差6。最先出现的差异列是x=158；不是全图色偏，而是少量取样边界选择了邻格，被阈值放大为明暗翻转。组合链会继续放大／传播差异。

相同夹具、同尺寸改采样格4（160×90工作面），阈值单卡固定帧逐字节一致。不能据此删掉格3用例或把可整除性能结果外推为任意尺寸可用。

## 独立坐标证据

`tests/browser/v4-gpu-resampling-diagnostic.mjs` 使用不含作品信息的像素编号条：源像素RGB编码其坐标，Canvas关闭平滑放大，再解码每个输出像素实际选择的源坐标，与现有Shader的公式比较。

本机 Edge 156.0.4314.42：

| 变换 | Canvas 与 `floor((x+.5)*from/to)` 的差异 |
|---|---|
| 214→640 | x=158：Canvas53／公式52；x=478：Canvas160／公式159 |
| 640→214 | 本次编号条无差异 |
| 160→640 | 无差异 |
| 640→160 | 无差异 |
| 63→187 | 本次编号条无差异 |
| 187→63 | 本次编号条无差异 |

首个坐标与真实编辑器差异列吻合。现有 `resampleFragment` 与范围输出Shader用数学像素中心计算最近邻索引；Canvas自身的坐标／栅格舍入并非所有比例下都等同于此公式。

这不是随机噪点种子、API调用耗时、播放12fps或“GPU并行导致不准确”。也不能仅靠把float换成整数，或统一增加一个epsilon，声称匹配所有宿主Canvas。当前证据未追踪Chromium具体实现分支，不把内部定点位数作为已经确认的事实。

- “所有场景画质一致／任意工作尺寸已验收”不能成立。此前小夹具通过不覆盖本次输入。
- 第4批的可整除格4性能结果只能作为该受限矩阵的数据；不代表本阻塞已解决，也不能作为默认GPU依据。

## 下一批建议：共享重采样基础设施，不重写各效果

先做独立原型，再改共享执行器：

1. 枚举多组源／目标尺寸（含整除、非整除、奇数、放大／缩小），对X/Y坐标分别提取Canvas实际选格映射。
2. 验证Canvas数值校准表是否能稳定代表正式CPU低分辨率读取／putImageData后的放大路径，并覆盖不同来源与表面复用；不要只匹配一张照片。
3. 通过后，缓存与素材无关的坐标表，GPU通过整数索引查询，而不是把逐帧作品图片读回CPU。表仅依赖尺寸、宿主语义和上下文代次，不依赖时间／颜色／seed。
4. 同一映射用于卡间缩小和最终／逐卡放大，保留每卡范围和既有效果顺序。检查纹理单位、最大尺寸、显式内存和初始化预算；超过可靠能力时整链CPU回退，不改产品参数范围。
5. 候选方案若不能严格复现，先增加明确的后端不支持条件与整链回退；不能因为平均误差小就放宽当前门禁。
6. 重跑既有Player严格画质、真实编辑器格3失败用例、可整除性能与生命周期。只有通过后，才更新能力声明和重新考虑对象内核复用。

当前未实施该方案，也未预先宣布它会无成本或跨设备一致。它涉及 `69a` 的共享重采样、能力描述、资源生命周期与定向夹具，不涉及Inspector、附着图样、参数时序或Agent必须提供Shader。

## 额外失败不可全部归因于选格

后续完整格4矩阵中，1920×1080的组合链仍有大差异；此外跨用例连续运行时，1280／1920的静态“无效果”对照出现差异，而这两边实际均执行CPU。独立新页面只运行1920无效果对照则逐字节一致。这提示另有顺序／持久表面／输入来源相关问题，尚未定位，不能把所有失败解释成上述非整除坐标。

已记录的1080组合单项诊断，两边实际时刻均为0.9000000000000004，图片绘制的smoothing=true、Alpha=.85及变换矩阵一致，因此也不能仅凭猜测归因于某处忘记切imageSmoothingEnabled。后续应先隔离CPU基线和图像来源，核对卡间输入，再判断具体GPU内核；不要直接改Shader掩盖输入差异。
