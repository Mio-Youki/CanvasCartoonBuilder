# Canvas → GPU 来源传递独立对照

状态：2026-10-15，独立诊断已通过；没有更换正式 Player、素材加载、导出或默认后端。

## 要回答的问题

真实 Player 的长主线程等待并不能单凭发生位置归因 shader。本轮先排除两个未经验证的假设：“把 Canvas 换成 ImageBitmap 就会更快”“只要 Canvas 每帧重画，上传就必然需要十几毫秒”。这不是完整 Player 性能验收。

## 方法与边界

夹具：`tests/browser/v4-gpu-source-transport.mjs`。Intel UHD 620、Edge／ANGLE D3D11；640×360 和 1920×1080；每路线预热 8 帧、记录 64 帧。第一轮正序、第二轮反序，减少固定执行顺序影响；仍是同一次浏览器启动内两轮短测，不是多设备／长时统计。

来源为 karsten 照片、非对称色块和椭圆，照片 Alpha 0.8，便于检测方向、颜色及透明度。每路线独立创建来源／输出资源；只执行纹理上传、复制 shader 和一次 GPU→Canvas 输出。保留每帧 GL 错误检查；没有不均采样、范围蒙版、双 Scene、对象胶囊或共享表面池。纹理在初始化时分配，不在播放中重建。

分别测来源绘制、上传 API、draw 提交、错误检查、最终 Canvas 输出和完整调用；上传／draw 的设备 query 不嵌套，读取与 `finish` 在播放结束后。固定画质比较也在计时后。主线程与设备区间可能重叠，不能相加推导完整帧，query 也没有覆盖所有 Canvas2D／驱动工作。

```text
node tools/tests/browser/v4-gpu-source-transport.mjs --write-report
node tools/tests/browser/v4-gpu-source-transport.mjs --bitmap-alpha --write-report
```

首轮 6 路线共 24 组：[基础结果](v4-gpu-source-transport-result.json)。补充 Alpha 表示后 7 路线共 28 组：[Alpha 对照结果](v4-gpu-source-transport-bitmap-alpha-result.json)。两份结果独立保留。所有组上传／draw 各有 64 有效设备样本（静态纹理复用没有播放上传 query），无 disjoint／GL 错误，最终 RGB、Alpha、预乘通道均与各自来源逐像素一致。

## 1080p 补充对照结果

完整调用包含本路线的来源绘制、上传、提交、验证和 Canvas 输出。区间为两轮读数，单位 ms；没有将准备位图的时间藏入播放计时。

| 来源路线 | 完整调用中位 | 完整调用 P95 | 说明 |
|---|---:|---:|---|
| 不变 HTMLCanvas，每帧上传 | 1.1–1.2 | 2.0–2.3 | 不重新绘制来源 |
| HTMLCanvas，每帧重绘相同内容 | 1.4–2.9 | 3.0–4.0 | 颜色相同，但重新提交绘制 |
| HTMLCanvas，每帧动画 | 1.4–1.6 | 3.1–3.2 | 椭圆移动，不能跳过上传 |
| OffscreenCanvas，每帧重绘相同内容 | 1.5–1.6 | 2.8 | 与正式表面池的来源类型相同 |
| 预备 ImageBitmap，非预乘 Alpha | 8.5–9.7 | 9.9–11.3 | 提前准备，播放仍每帧上传 |
| 已上传静态纹理直接复用 | 1.1 | 1.5–2.0 | 仅静态下限对照，不适用于变化画面 |
| 预备 ImageBitmap，预乘 Alpha | 1.1–1.2 | 1.6–2.0 | 复制 shader 按 Alpha 还原 RGB |

非预乘位图的提前准备为 20.5–22.8 ms，播放上传 API 本身中位 6.9–7.8 ms；预乘位图提前准备约 0.2 ms、上传 API 中位约 0 ms。两种位图的设备上传中位约 0.87–1.05 ms，远小于非预乘位图主线程上传调用，说明设备区间不能解释全部来源转换成本。具体慢路径由 Alpha 表示引发是本组对照支持的推断，尚无浏览器／驱动内部 trace，不能声称已定位到某个内部函数。

位图都预先翻转 Y，颜色空间转换选 `none`；预乘路线额外在 GPU 复制 shader 除以 Alpha，故最终显示保持一致。此处没有测试任意颜色配置、极低 Alpha、渐变边缘或所有采样／加样算子；不是“把预乘位图塞进现有 shader 即可”的迁移方案。原 Runtime 仍按既有颜色／Alpha 合成合同工作。

## 结论与不做的事

1. 普通 Canvas／OffscreenCanvas 的独立传递没有复现真实双 Scene 的二十几毫秒完整调用；不能把完整 Player 卡顿归结为 Canvas 这个类型。
2. ImageBitmap 不是天然更快或更慢，Alpha 表示会显著影响本机路径。不能因基础对照中的非预乘路线慢，就否定全部位图方式；也不能凭静态预乘路线快就替换每帧动态来源。
3. 预备位图和静态纹理复用都没有包含“为动态场景每帧重新生成快照”的成本；当前同步 `renderTo` 不能凭空获得新的异步位图。本轮不引入每帧 `createImageBitmap`。
4. 静态纹理复用的收益以来源确实不变为前提。正式来源／蒙版的版本和失效机制仍需覆盖动画、编辑、素材解析、撤销与切换；本轮不以牺牲正确性跳过上传。
5. 复制 shader 没有完整 Player 的多来源、表面池复用、反复 Canvas2D／WebGL 合成依赖，必须回到真实 Player 独立改变一个变量再验收，不能把这里的 1–4 ms 当成产品最终帧预算。

## 下一步

以真实 Player 为主体，记录来源、工作图和范围图的表面身份／复用关系，并对照固定角色表面与通用池复用，判断是否存在反复读写同一 backing 的依赖或迁移。结合已测试的同帧合并验证，先做重复／长时对照；只在真实 Player 的预算、画面、回退与资源验收都支持时，才考虑固定角色资源或预乘内部表示。效果整链扩大、宿主释放／版本、Tauri 和默认 Auto 后端仍是独立未完成项。
