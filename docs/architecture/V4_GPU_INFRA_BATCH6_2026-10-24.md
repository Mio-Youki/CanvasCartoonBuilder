# GPU 基础设施第 6 批：原生最近邻坐标校准可行性

日期：2026-10-24。状态：**数字校准方案通过本机 160 组二维 Canvas 对照；尚未接入 Runtime。非整除编辑器画质阻塞尚未关闭，默认 CPU 不变。**

## 本轮范围

沿用第 5 批的整数坐标修复，不重新实现效果、不修改 Inspector、作品 JSON 或另一会话的图样模块。本轮先验证一个替代经验 epsilon 的方案：让本机 Canvas 对像素编号条做一次最近邻缩放，得到 X/Y 实际选格表，再考虑由 GPU 使用该表。

校准输入仅为不透明数字编号；长度是轴尺寸，不是作品像素面积。没有读取作品、生成噪点帧、测量 GPU 执行时间，也没有产品中的逐帧 CPU 回读。

## 文件

- `tests/browser/helpers/native-nearest-calibration.js`：实验性数字条校准函数，显式区分轴、Canvas 类型和 willReadFrequently。
- `tests/browser/v4-gpu-native-nearest-calibration.mjs`：严格二维画面对照；任意 RGBA 字节差异均失败；测试失败时仍保存报告。
- `docs/architecture/v4-gpu-native-nearest-calibration-2026-10-24-result.json`：160 组原始结果。

函数刻意仍位于测试目录，未加入 Runtime 构建清单。不能据此声称生产 GPU 已支持校准或完成资源／缓存生命周期。

## 验证与发现

运行：`node tests/browser/v4-gpu-native-nearest-calibration.mjs --write-report`。

本机 Edge 156.0.4314.42，headless。10 组尺寸方向 × 2 种 Canvas × 2 种读取模式 × 2 种透明度 × 2 种输入来源 = 160 组。

尺寸覆盖：214×120 ↔ 640×360、187×105 ↔ 63×35、333×187 ↔ 1000×561、480×270 ↔ 1920×1080、7×11 ↔ 19×31。输入来源为 putImageData 和经另一 Canvas 绘制的副本。

结果：**160/160 组 RGBA 全字节一致，40 组的校准坐标至少一轴不同于数学最近邻公式。** 这不是性能基准，不提供 P95 或跨设备保证。

重要发现：同一尺寸不能直接共用一个全局校准结果。例如本机 214→640：普通 Canvas 有 2 个 X 坐标与数学公式不同，willReadFrequently 模式为 0；1920→480：普通模式为 0，频繁读取模式所有 480 个坐标均不同。两种模式各自的编号条均能复现本轮对应的二维绘制。

因此，不能把软件读取模式下的“通过”作为普通预览的结论，也不能为修复 GPU 而强行改变 CPU Canvas 的读取属性。

## 下一批接入设计与边界

1. 校准与实际 CPU 表面创建方式、读取属性、尺寸、上下文代次绑定；不得仅按尺寸永久全局缓存。运行中 backing 变化的检测／保守失效仍须验证。
2. 缩小和放大分别校准 X/Y。与数学公式一致时保留现有整数 Shader；有例外时才创建上下文拥有的 R32UI 坐标纹理，供共享 resample/output 内核消费。
3. 建议 4 行表分别存 down-X/down-Y/up-X/up-Y，最大轴宽 W 的显式纹理内存为 16W 字节；实际采用前检查设备尺寸限制。该估算不是已经发生的资源开销。
4. 单独记录校准 CPU 准备耗时、初始化上传、坐标纹理字节与释放。不能把校准读取列为逐帧作品回读，也不能隐藏初始化成本。
5. 校准失败、模式无法确定或设备不支持表尺寸时，整链 CPU 回退并提供明确原因；不修改产品参数范围，不做逐卡 CPU/GPU 往返。
6. 必须重新运行真实编辑器格 3 矩阵、格 4 回归、修改／撤销／seek／改尺寸／项目切换和资源释放。只有这一步通过，才能修改能力合同中的 known-failing 声明和界面警告。
