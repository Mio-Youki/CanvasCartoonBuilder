# ASCII原图背景与对象迁移评估

## 已落地：场景ASCII原图背景

1. Registry：`originalBackground=false`；开启后渐进显示`blend=normal`，提供既有12项原生混合，无Dissolve／Hard Mix。背景颜色与Alpha隐藏且不参与绘制，关闭后恢复原值。沿用效果轨Step，非Linear。
2. Inspector：既有参数生成器直接消费visibleWhen；无需新颜色控件或独立面板。
3. Runtime：CPU和GPU先输出透明字符层，再在池化合成面上绘制当前输入，并以所选混合绘制字符层。保留既有单色／原色字符选择。所谓原图＝ASCII本阶段的输入（包含此前效果），不是原始素材，也不是冻结场景截图。场景效果蒙版继续由外层统一管理。
4. 测试：`tests/browser/v4-ascii-original-background.mjs`接入verify-v4。逐像素比较12种混合与手工Canvas合成；透明输入、字符透明度0完整保留原图、CPU/GPU、Step及seek、渐进显隐、撤销、工程恢复、HTML播放。

额外成本是一张输入等大的池化RGBA合成面和两次drawImage；不增加字体烘焙、Sobel分析或逐像素JS混合。1920×1080的一张逻辑RGBA面约7.91MiB，实际浏览器backing／GPU占用依实现。关闭不走该分支。混合走Canvas原生，不保证所有设备耗时一致；定向测试包含360p／1080p预热后墙钟测量，不是整个编辑器FPS承诺。

本机Edge定向参考（静态输入、无边缘强化、Auto后端、预热4次后10次采样，同时存在其他回归任务，仅供量级参考）：360p中位4.7→4.8ms，1080p中位11.4→13.3ms、P95 12.3→13.7ms。不是动态多效果／多对象的性能结论。

验收结果：上述定向测试通过，CPU/GPU最大通道误差0；状态合同、Runtime smoke、构建／内联／manifest一致性检查及完整verify-v4通过。本轮未重打Tauri安装包。

## 对象迁移：可行，但本次未开放

> 此节保留初次评估记录；后续用户确认后已迁入对象，当前合同见[V4_ASCII_OBJECT_2026-10-17.md](V4_ASCII_OBJECT_2026-10-17.md)。下述“未开放”只描述评估时点。

当前Registry只开放scene；对象sampling.apply尚未调用ASCII，直接扩大scope会出现“有入口无效果”。算法本身接受Canvas，不强制原始图片，因而图片、文字、多图元、程序对象均可处理已渲染的对象胶囊，无需拆成字符实体或新增字体资产。

安全迁移需要四个落点：

- Registry：scope／readiness／cost增加object；对象胶囊开销声明为高成本，动画粒子若继承则需共享结果，不逐粒子运行ASCII。
- Runtime：在对象基础采样格与其他采样处理完成并恢复全尺寸后调用ASCII，位于采样末端，不能直接塞入降分辨率applyFull再重复乘采样格；沿用mask/decorate/sample调序及最后对象Alpha／混合。
- 几何：明确字符格以对象局部坐标锚定；外扩装饰和图元使胶囊边界变化时不能无故移动格点。透明边界当前按单元代表Alpha，非逐源像素裁切，整字可能越出原轮廓；需选择保持完整字形还是额外裁边，不能默默改变对象选择框。
- 验收：图像／文字／多图元／程序对象、旋转缩放、三阶段调序、蒙版、原图背景、Step／撤销／导出，以及多对象性能和atlas切换。场景当前每SurfacePool一个GPU上下文可共享，不应每对象创建上下文；不同图集交替会重传字形纹理，需要专项缓存预算。

结论：技术上适合迁入对象，成本主要取决于对象胶囊像素面积、数量、边缘分析和图集切换，并非字体本身。单对象局部面积小通常比全场景便宜；多个大对象可能更贵。本次只实现用户明确要求的场景新参数，并提交对象评估，不把可行性检查冒充对象已支持。
