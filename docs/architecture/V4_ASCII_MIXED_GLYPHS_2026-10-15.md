# ASCII默认字体：保留内置字形，统一格扩展

历史阶段：此处描述8×8修复。当前已升级为[寒蝉16px＋16×16混合图集](V4_ASCII_16PX_IMPLEMENTATION_2026-10-15.md)。同名测试、JSON与对照PNG已更新为16px版本，下面的8px字节／系统回退描述不代表当前默认实现。

## 修复问题

旧`prepare`要求所有字符都存在于内置bitmap才使用位图路径。新增一个字母／中文，就把整套符号与方向字符切换为24px系统monospace，按最宽字符重建32px高的图集。其后统一缩放使原符号变细／缩小，造成整体变暗。

现在`font=builtin`始终使用固定8×8格：

1. 内置字符／方向字符直接复制原掩码，逐像素不变。
2. 仅扩展字符在固定32×32 em格中按24px monospace绘制，再平滑缩为8×8灰度Alpha。普通字符保持相同em尺度，不随字符集的最大宽度变化；极长字素按advance缩小以免溢出，不采用各字符可见紧框撑满。
3. 全部掩码合成一张统一图集后，再计算每个字符最终Alpha覆盖率，建立同一疏密序列和亮度LUT。
4. 主动选择默认无衬线／导入字体时，仍整套采用所选字体原有烘焙逻辑。不会偷偷混入内置符号。

## 排序／画面边界

密度定义为最终格内`sum(alpha)/(255*64)`。不查询“系统字体中原本的#”，不预设中文比@更密，不用字符名字、输入顺序或Unicode分类替代最终测量。

新增字符可能被亮度LUT选中，因此整幅画面仍可能发生合理变化；本次保证的是原字形、统一格和其覆盖率不被连带改写，不保证扩展前后整幅画面完全一样。等Alpha也不保证相同感知粗细；不自动加粗扩展字符，不伪造覆盖率。

8×8中文辨识度有天然上限，扩展字形也可能比硬边位图更柔和。需要更细腻、整套一致的文字风格时，应主动选择其他字体，不为此暗中扩大默认格。

扩展字符第一次烘焙时取决于当前环境的monospace及缺字回退。Edge与WebView可产生不同Alpha；各自内部排序都按自身最终Alpha计算。工程／导出保存完整图集，之后播放不再需要这些字体。

已经保存的`glyphAtlas`继续按原数据播放，不静默替换旧作品。旧图集若来自整体回退，需要修改字符集，或切到其他字体后再切回默认字符字体，触发一次重建。没有新增schema版本或永久兼容层。

## 缓存与性能

- 仍为原12项有限图集缓存；没有为每个字符新增持久Canvas、GPU上下文或独立纹理。
- 仅编辑／首次缺少图集时绘制扩展字符，临时复用一张32×32和一张8×8 Canvas；播放只消费合并图集。
- 原默认10个字符＋4方向字符：896字节原始Alpha；新增A、a、中、界后：1152字节，增加256字节。Base64序列化另有编码开销；这不是整个工程文件或GPU实际显存大小。
- 连续20帧测试：`fillText`／`measureText`调用0，当前GPU图集上传1次。同配置复用同一atlas对象。未增加逐帧字符排序或字体查找。
- 本轮不重新宣称FPS；字符集变化后可选字形更多，播放绘制路径本身不变。

## 已验证

- 14个原字形在增加4字符及更宽字符后逐字节相同；A／a／中／界不为空，加入宽字符不会改变它们。
- 所有密度与最终Alpha精确一致；256个亮度LUT项按最终覆盖率择近。
- 相对尺寸／字形比例不被新增字符改变；主动换字体仍走整套原生字体路径。
- 20帧缓存／字体调用／上传检查；序列化后把字体ID改为不可用ID，已烘焙图集仍输出相同像素。
- 真实Inspector输入、撤销、项目打包／恢复和自包含HTML就绪均通过。
- 状态合同、Runtime smoke、原ASCII浏览器流程、40组CPU参考对照、22组GPU精度／回退／释放检查均通过；构建源与镜像current检查通过。
- 真实Tauri WebView的同一字体检查通过（现有exe临时加载v4，不改默认入口）。第一次受限环境CDP连接超时，正常桌面权限重试通过；不是把连接超时当成产品字体失败。
