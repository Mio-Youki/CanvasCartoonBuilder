# 真实 Player：同页交错连续压力验收

状态：2026-10-15，本机压力测试完成。未修改 Runtime、默认后端、验证策略、表面策略或 UI。

## 本轮问题与方法

回答：短测中的大间隔是否都来自启动？固定角色／帧末合并检查是否在持续播放中稳定占优？

夹具：`tests/browser/v4-gpu-player-interleaved-playback.mjs`。短测与本夹具共同使用 `tests/browser/fixtures/v4-gpu-player-fixture.js`，避免场景内容在两套测试中漂移：1920×1080、照片＋八个动画矩形、动态引用范围、不均采样波场、双 Scene GPU 淡入淡出。两侧保持各自运动。

四个 Player 常驻同一个 Edge 页面，各一个 GPU 上下文：通用池／逐侧检查、通用池／帧末检查、固定角色／逐侧检查、固定角色／帧末检查。每个 Player 首次绘制单列，再同步预热至八次；四轮采用平衡位置及前序次序的交错顺序，每轮每策略连续绘制一段，而非同时执行四个 renderTo。初始化顺序不平衡，不能比较不同策略的首次绘制成本。

```text
node tools/tests/browser/v4-gpu-player-interleaved-playback.mjs --write-report
node tools/tests/browser/v4-gpu-player-interleaved-playback.mjs --block-frames=450 --write-report
```

前一条每段 180 帧，每策略 720 帧；后一条每段 450 帧，每策略 1800 帧，合计 7200 帧。主结果测量窗口约 **146.06 秒**，不含初始化、最终画质回读与释放。

为让每帧都承担双侧工作，播放时钟循环在入场淡入的 1.8 秒窗口内；这是一种重复转场压力，不是自然运行完整八秒工程。不同策略使用相同逻辑时钟序列，但不是按 wall-clock 丢帧推进；不测编辑器交互、其他转场、完整 GPU 效果链、Tauri 或设备休眠恢复。本轮没有 timer query，以减少诊断命令干扰。四个常驻上下文的资源驻留也不同于先前单 Player 测试，不能直接比较不同轮的绝对耗时。

## 计时区分与一次纠正

同时记录：

- 完整 `renderTo` 的主线程调用时间；
- 相邻 RAF **参数时间戳**的差值；
- `performance.now()` 记录的回调实际到达间隔；
- 回调到达时间减 RAF 参数时间戳的滞后。

本轮首个条件 RAF 时间戳间隔最大 **1015.7 ms**，其时间戳滞后最大 **1001.7 ms**，实际回调到达间隔最大只有 **58.4 ms**。前一版 720 帧补测也出现类似结果（915.9 ms／904.7 ms／40.6 ms）。因此不能将这个约一秒数值解释为某次 renderTo 或两次实际回调之间卡住一秒。

这不证明所有旧尾帧都是假象，也不代表浏览器呈现一定正常；本测试没有浏览器 compositor／屏幕呈现 trace。先前仅记录 RAF 参数间隔的“最大帧间隔”应保留其原始定义，**不再直接等同于绘制卡死时间**。首次初始化确有较长同步调用，四实例分别约 304.6／96.6／116.4／117.0 ms，冷暖缓存与顺序不同，不能据此评判资源策略。

## 主结果：排除每策略最初 60 帧后

Intel UHD 620／ANGLE D3D11／Edge，同一页平衡交错；每策略剩余 1740 个绘制样本。单位 ms。

| 策略 | 绘制中位／P95 | 绘制最大值 | 实际回调间隔 P95／最大 | RAF 参数间隔 P95 |
|---|---:|---:|---:|---:|
| 通用池＋逐侧检查 | 19.4／22.8 | 50.5 | 24.4／58.4 | 33.4 |
| 通用池＋帧末检查 | 18.6／22.8 | 101.9 | 24.5／113.1 | 33.4 |
| 固定角色＋逐侧检查 | 19.7／24.4 | 45.4 | 26.0／47.0 | 33.4 |
| 固定角色＋帧末检查 | 18.2／21.7 | 35.5 | 23.2／36.3 | 33.3 |

持续阶段并没有自动回到 16.7 ms：各条件 P95 都超过 60 fps 单帧预算，而且通用池＋帧末检查确有两次超过 50 ms 的真实绘制调用，不能全部归咎启动时间戳。30 fps 预算在这组 P95 层面更宽裕，但最大值仍超出预算，不能承诺无掉帧。

固定角色＋帧末检查在本轮部分指标最好，但前一版 720 帧补测中，绘制 P95 分别为 20.6／20.0／19.9／20.7 ms，排名并不稳定。多个条件的最后一段耗时较高，也没有温度／频率或系统负载 trace 来断言原因。单设备一次长测不足以将 1–2 ms 的差异推成默认策略。

## 画质、资源与证据

- 四种策略最终固定时刻与 CPU 基线逐像素一致。回读在全部计时完成之后，不改变测量阶段的 Canvas backing 策略。
- 每帧检查真实 GPU 两侧及最终合成后端，未出现隐藏的 CPU 回退。
- 预热后所有条件的纹理分配、上下文数量、Canvas backing 尺寸写入及父／子固定角色分配数保持不变；每 Player 六张显式 GPU 工作纹理约 33.398 MiB，四个实例总共四个上下文。
- 最后逐个 dispose，四个上下文均已释放。未测 JS heap、浏览器／驱动内存峰值，不能把这些计数不变写成“没有任何内存增长”。
- 原始样本、每段统计、前 16 帧恢复统计、最初 60 帧／后续帧统计均保留。

## 收束决定

1. 资源策略继续默认通用池，不推广固定角色。它证明了隔离可行，但没有稳定且足够的性能优势。
2. 帧末合并检查继续是显式 GPU 转场实验选项，仍在输出前检查并当帧 CPU 回退，不改默认验证合同；它是批量提交，不是真正异步呈现。
3. 不再用重复的来源类型／表面策略短测追逐微小差值。保留已有证据，后续优先按生产顺序扩大真实 Player 整链，并接宿主版本与释放生命周期；在这些具体变化后再统一跑预算。
4. 稳定 60 fps、跨设备、真实编辑器、导出和 Tauri 仍未通过；这组成绩不构成默认 Auto GPU 上线条件。不要以降低画质、跳过来源更新或放弃错误回退隐藏尾帧。
