# ASCII动态P95与边缘分析隔离实验（2026-10-15）

## 结论与当前状态

推荐的落地候选是 **低分辨率GPU边缘分析＋独立CPU选字函数／复用缓冲**，不是直接启用全分辨率检测。本机1080p照片动态夹具P95从116.4ms降至27.2ms（约下降77%）。没有GPU分析时，可以先采用CPU分析优化与函数拆分，本机P95为48.6ms。

**本轮仅新增实验脚本／夹具／报告和实图，未修改正式Runtime、Registry、Inspector或导出。编辑器仍运行原实现。**所有候选保持已有GPU最终字形合成；这里的“CPU优化”指分析／选字，不是无GPU的完整CPU绘制性能。

## 方法与公平边界

- Windows、Edge155、ANGLE D3D11、Intel UHD Graphics620。硬件GPU单机结果，不能外推到软件WebGL／移动端／其他驱动／Tauri WebView。
- 相同karsten照片，逐帧重画输入中的小型运动条，并叠加对象bob；完整`Runtime.renderTo`处理相同动态内容。场景只含图片对象，不是复杂多对象／多效果编辑器压力测试。
- 640×360、1280×720、1920×1080；每档预热12帧，60帧采样。默认相对尺寸8、字形比例2/3、采样格1，检测灵敏度.75、显示阈值.25，原色字符。
- 同时记录JS调用墙钟、ASCII上下文`gl.finish()`后总耗时、RAF帧间隔、分析读回／边缘／选字／合成分段耗时。P95取排序后的95%分位，不用shader提交时间代替全帧。
- `gl.finish()`保证该WebGL上下文完成，不保证操作系统已经显示该帧；不是GPU timer query。RAF数据来自headless浏览器，也不是整个编辑器含Inspector的实际呈现FPS。
- 计时期间不做输出像素读回；画质比较另行进行，避免把截图／getImageData开销混入帧时间。输入重画本身不包含在renderTo计时内，但反映在RAF间隔。
- 四种素材的固定时间640×360输出比较逐通道／Alpha，保真候选误差非零会拒绝。**这不等于所有尺寸、每个动态时刻、字体、边缘参数、蒙版都已逐像素验证。**正式迁入前要扩大组合夹具。
- 第一轮quick曾测出1080p基线155ms、CPU优化79ms、GPU低分辨率48ms；扩大预热／60样本后数值改变，说明JIT／样本长度与系统抖动影响明显。以下仅使用第二轮同配置正式结果，不混搭最好数值。

## 动态完整帧结果

数值为中位／P95，单位ms，包含末端GPU同步。

| 路径 | 640×360 | 1280×720 | 1920×1080 |
| --- | --- | --- | --- |
| 当前基线 | 16.9 / 34.2 | 38.9 / 46.9 | 92.5 / 116.4 |
| 仅CPU边缘优化 | 9.2 / 12.7 | 24.3 / 36.0 | 82.0 / 106.4 |
| CPU边缘＋选字函数／缓冲优化 | 8.4 / 10.6 | 19.5 / 23.7 | 40.9 / 48.6 |
| GPU低分辨率边缘 | 8.3 / 10.6 | 16.2 / 20.8 | 32.0 / 37.1 |
| GPU低分辨率边缘＋选字优化 | 6.7 / 7.9 | 11.3 / 12.8 | 23.9 / 27.2 |
| GPU全分辨率边缘（选字保持基线） | 9.1 / 11.6 | 20.8 / 24.7 | 43.3 / 50.3 |

比较全分辨率的额外成本时应对照“GPU低分辨率边缘”37.1ms与“GPU全分辨率边缘”50.3ms，两者的选字优化条件一致；不能把27.2与50.3的全部差额归因于分辨率。

1080p基线阶段中位：准备／低分辨率读回14.3ms，边缘62.6ms，选字13.6ms，合成.7ms。最优候选阶段中位：准备／读回16.7ms，GPU边缘提交1.6ms，选字4.4ms，合成.6ms；其最终同步后的总P95仍为27.2ms。阶段分位不能相加得出总分位；GPU排队／上传等待可能落在后续读回阶段。

最优候选1080p RAF中位24.3ms、P95 27.6ms，最长36.3ms；完整绘制最长34.8ms。因此有30fps预算潜力，但**不能宣称所有帧／完整编辑器已稳定30fps**。

全分辨率照片约2.02%的通道发生变化。这不是单纯浮点误差：高斯尺度从“分析像素”变为“原图像素”，参与投票的像素范围与证据比例也变了。实图中部分轮廓反而减少、细线未自动变得更易辨识，文字方向字符分布改变。当前版本**尚未通过替换画质门槛**，不能据“分辨率更高”直接认定更好。

后续要独立校准原图空间的sigma／核范围与显示阈值，增加细线召回和无噪声区域误检的量化；保留低分辨率外观作为参照。全分辨率是未来质量选项候选，不是此次无感性能优化。

## 优化内容及开销

### 保真CPU候选

- 预计算高斯核，两个尺度的横向／纵向计算合并遍历；保留各方向原有Float32舍入。
- 复用亮度／横向结果／DoG／投票／方向数组，DoG二值结果用Uint8而非Float32。
- 用绝对梯度比值判定四方向，替代逐点atan2；对应22.5°分界，不修改方向定义。
- 单元选字拆成独立小函数，复用颜色／索引缓冲，避免继续扩充超长apply函数。
- 分析性能改善已测得；数组分配减少是代码事实，但未做GC trace，不能把全部P95改善都声称为GC减少或某一种JIT原因。

### GPU低分辨率候选

- 仍使用原Canvas4×4分析数据；GPU执行双高斯差分、方向检测、单元投票。
- 与已有ASCII字形合成共用上下文；方向结果直接留在纹理中，不读回CPU后再上传。
- 源颜色与Alpha代表样本仍按原CPU路径计算，因此此次四类素材可保持完全相同外观。
- 需要可渲染Float纹理；不可用时正式版应回退优化CPU分析，不能强制依赖。本轮在不支持该扩展的设备上会报告候选不可运行，而不是假装通过。
- 本实验固定字形单元8×12，全分辨率投票循环最多覆盖64×64。不是任意大小、任意采样格的完整生产实现。
- 仅分析纹理理论容量：低分辨率约9.8MB，全分辨率约58.1MB（包括源RGBA、双尺度水平Float、DoG、方向、投票；不含Canvas backing、最终输出、字形图集与驱动开销）。前者比为每效果单独新建完整GPU上下文更适合轻量路线。
