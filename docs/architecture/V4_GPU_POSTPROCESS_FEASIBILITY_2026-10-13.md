# V4 场景级 GPU 后处理与网点映射可行性测试（2026-10-13）

## 本轮边界

这是**隔离性能试验**，没有修改正式 Runtime、效果 Registry 或导出格式。可重复运行：

```powershell
node tools/tests/browser/v4-gpu-postprocess-benchmark.mjs
```

追加 `--raw` 可得到每次计时样本。测试脚本在本地 Edge 中加载 v4 Runtime，以相同的合成图输入，比较现有 Canvas2D 路径与一个仅供基准使用的 WebGL 原型。GPU 计时**包括**每帧从 Canvas 上传输入、GPU 处理、将 WebGL 画布绘制回 Canvas2D；CPU 计时包括现有模块处理与绘制到可复用的输出画布。两侧均复用输出画布；每项预热 3 次后采样 10 次，1920×1080 为 6 次。数字是浏览器调用的墙钟耗时，不是 GPU query，也不包含完整场景对象绘制、Inspector、播放调度或导出打包。

设备：Windows / Edge 155 / ANGLE Direct3D11 / Intel UHD Graphics 620；这是**有硬件 GPU 的单机结果**，不能外推到软件 WebGL、其他驱动或移动端。测试输入为可重复的彩色渐变＋图形合成画面；额外测试透明椭圆对象。

## 连续像素滤镜：调色四轴

GPU 原型使用与现有 `sceneEffects.colorGrade` 一致的色相、亮度、对比度、饱和度公式。三次连续调色用于模拟多道全画面像素滤镜的纹理链，**不是产品中同时启用三张相同卡片**。中间两道使用同一个 WebGL 上下文的 framebuffer texture，输入只上传一次，最终输出一次。

| 画面 | 道数 | CPU 中位 / P95 | GPU 中位 / P95 | 像素平均通道误差 |
| --- | ---: | ---: | ---: | ---: |
| 640×360 | 1 | 11.0 / 11.2 ms | 0.9 / 2.0 ms | 0 / 255 |
| 640×360 | 3 | 41.0 / 56.3 ms | 2.3 / 2.5 ms | 0.01 / 255 |
| 1920×1080 | 1 | 83.5 / 99.6 ms | 14.3 / 17.3 ms | 0 / 255 |
| 1920×1080 | 3 | 265.3 / 290.7 ms | 16.0 / 17.6 ms | 0.01 / 255 |

结论：共享纹理链对**对象合成后的场景级连续调色**有明确潜力，且本次公式/输出已达到几乎一致。它不能据此替代所有场景滤镜：纹理叠加、蒙版、Hard Mix 等需要独立的顺序和混合验证。尤其不能把多个独立 WebGL 效果简单串成“上传→读回→再上传”。

## 网点映射：两道 GPU 原型

原型第一道在低分辨率纹理中分析色彩与中心 Alpha，第二道在全尺寸画面根据网格中心、亮度和阈值画圆点。现有 CPU 实现则用 Canvas 缩图的高质量平滑读取、另一张最近邻 Alpha 读取，以及 Path2D 批量印点。因此这是**相同功能方向的试作，不是逐像素保真的移植**。

| 条件 | CPU 中位 / P95 | GPU 中位 / P95 | 平均通道误差 | 大误差像素占比¹ |
| --- | ---: | ---: | ---: | ---: |
| 640×360，圆点，单元 8，0° | 28.6 / 32.6 ms | 2.1 / 2.3 ms | 7.10 / 255 | 4.38% |
| 640×360，圆点，单元 8，45° | 28.5 / 30.9 ms | 1.8 / 2.0 ms | 7.07 / 255 | 4.36% |
| 640×360，透明对象，单元 8 | 13.0 / 15.6 ms | 1.1 / 1.2 ms | 3.38 / 255 | 2.14% |
| 640×360，单元 2 | 154.4 / 194.3 ms | 2.1 / 2.3 ms | 8.75 / 255 | 0%² |
| 640×360，单元 16 | 16.7 / 18.9 ms | 1.6 / 1.9 ms | 3.97 / 255 | 2.27% |
| 1920×1080，单元 8 | 148.0 / 163.4 ms | 18.1 / 19.0 ms | 6.99 / 255 | 4.58% |

¹ 单像素四通道平均绝对误差超过 32/255 的比例。² 单元 2 时，这个指标掩盖了严重的 Alpha 覆盖差异：**Alpha 大于 127** 的像素占比，CPU 为 1.41%，GPU 为 15.75%；这不是“所有可见像素”的占比。CPU 仍留下大量低 Alpha 的亚像素痕迹，小点的覆盖规则与 GPU 原型不等价，**不能以该行的大误差占比为零宣称画质通过**。

运行 `node tools/tests/browser/v4-gpu-postprocess-benchmark.mjs --capture-cell2` 可重建同一输入、同一参数的实图：[CPU 全图](./v4-halftone-cell2-cpu.png)、[GPU 全图](./v4-halftone-cell2-gpu.png)；[CPU 深底](./v4-halftone-cell2-cpu-dark.png)、[GPU 深底](./v4-halftone-cell2-gpu-dark.png)；[CPU Alpha 局部 8 倍](./v4-halftone-cell2-cpu-alpha-zoom.png)、[GPU Alpha 局部 8 倍](./v4-halftone-cell2-gpu-alpha-zoom.png)。局部图取两张全图相同的 64×64 区域，最近邻放大；灰度直接表示原输出的 Alpha，未额外阈值化。

网点结果说明 GPU 后处理在数学和性能上可行，特别是点密时免去大量 Path2D mark；但当前画质还未达到替换门槛。差异主要来自低分辨率分析滤波、Canvas Path2D 与 shader 的亚像素圆边、极小圆点的覆盖规则，而不是单纯的速度问题。原型只覆盖“圆点＋原色”、0°/45°、透明对象；尚未覆盖其他点形、单色/灰度、运动相位、场景蒙版、采样格与其他效果组合。

## 对「场景 / 加样 / 采样」的决定

1. **场景级后处理：可进入下一步。** 以共享 WebGL 上下文＋两张中间纹理做一条可选管线；先迁入已验证视觉公式的连续调色，测完整 `renderTo` 的 RAF / render P95、内存与多效果顺序。WebGL 不可用或 context lost 时保留 CPU 路径。
2. **场景网点：暂不替换。** 先在固定时间画质夹具里补齐单元 2/8/16、0°/45°、透明边缘与全部色彩/点形。目标不仅是平均误差，还包括网点 Alpha 覆盖和边缘无溢点。再测试与前后采样效果、蒙版组合的结果。
3. **对象采样 / 加样：不能直接“放入场景末端”。** 对象阶段发生在 z 合成之前，可被对象蒙版、混合方式和相邻层影响。若要 GPU 化，需共享同一上下文处理**对象胶囊**并按原顺序回到场景合成；为每个对象独立建 WebGL 上下文或反复 GPU↔CPU 往返不可接受。透明对象单项测试只证明可画，不证明多对象全帧更快或语义正确。
4. **时间轴 Linear：独立决策。** GPU 让每帧重算某些连续像素参数更便宜，但时序插值规则、静态/动态叠加、整数格点跳变和导出一致性仍需分别定义。当前加样已有部分 `linear-safe` 数值/颜色参数；采样尺寸、点形、色板、随机种子等仍应保持 Step。待完整帧预算和效果逐项视觉夹具通过，才讨论扩大采样的 Linear 白名单。

### 下一轮验收门槛

- 同场景 CPU/GPU 固定时刻画质对照与导出一致；极小网点的 Alpha 占有率不得出现本轮 1.41%→15.75% 这种偏差。
- 640×360、1280×720、1920×1080 的完整播放器渲染 P95，以及静止画面跳帧/缓存行为，不能只看孤立 shader。
- 多对象（至少 1/10/50 胶囊）、混合方式、蒙版、阶段重排、场景过渡；量化 GPU↔CPU 交界次数和纹理峰值内存。
- 软件 WebGL 或无 WebGL 的回退路径仍可产生同样可接受的画面；Tauri 与独立网页测试场景都要覆盖。

本文件记录可行性，**不代表已决定把网点映射或所有加样/采样切到 GPU**。

## 下一轮：以场景后处理为载体的效果筛选实验

### 原则与优先级

测试对象只取已经合成完毕、确实属于**场景滤镜**的画面。现有场景顺序是采样滤镜（颜色映射、杂色抖动、阈值分色、偏移采样、网点映射、不均采样、边缘色散、CRT）与叠加滤镜（调色、染色、纹理、蒙版暗角、颗粒）的固定内部顺序。测试不能把对象级投影、描边、内外光等搬到场景末端冒充等效；对象效果仍在 z 合成和对象蒙版之前。

| 批次 | 候选 | 预期 GPU 价值 | 必须验证的语义风险 |
| --- | --- | --- | --- |
| A | 阈值分色、杂色抖动、染色叠加、边缘色散 | 连续或邻域像素操作，适合单纹理 pass；可与已验证调色共用上下文 | 颜色/Alpha、seed 与时间确定性、透明边、蒙版及混合方式 |
| B | 颗粒叠加、纹理叠加（先静态图案）、蒙版暗角、Hard Mix | 可在 GPU 生成场或合成，减少全画布中间 Canvas | 噪声节奏和复用缓存、图案相位、混合公式、蒙版边界；不能只比单 shader |
| C | 颜色映射、偏移采样、不均采样、网点映射 | 当前 CPU 有像素读回或大量 marks，理论收益高 | 调色板构建、采样格规则、动态场、极小网点 Alpha；允许 GPU 前处理后才作为候选 |
| D | 对象投影／描边／内外光 | 本轮不进入场景末端测试 | 改变 z、蒙版、裁切、混合顺序；须另立对象胶囊共享 GPU 试验 |

### 可重复流程

1. 保留现有生产 CPU 实现为基线；每个候选只在隔离原型中加 shader，**不动 Registry、项目格式或导出**。以同一输入、同一配置、同一固定时间生成 CPU/GPU 图；比较浅底、深底、Alpha 和差分图。
2. 单效果先测 640×360、1280×720、1920×1080；画面覆盖照片、透明图片、矢量、文字、10 层混合场景。静态、动态、蒙版、前后相邻效果各一组。输出平均通道误差、大误差比例、Alpha 总量和边缘溢点数量；对有随机性的效果先固定 seed/时间。
3. 再测一条**共享 WebGL 上下文＋双中间纹理**的场景管线：同帧只上传合成画面一次、最后只回到 Canvas 一次。分别统计单效果、2/4/8 效果连用与“每效果独立 GPU 往返”的成本，明确速度来自计算还是减少数据搬运。
4. 在完整 `renderTo`／播放调度中记录冷启动 shader 编译、稳态 P50/P95、跳帧、纹理峰值内存、上传/回读次数；测试 Auto/Draft、场景过渡、静止帧缓存、导出独立 HTML、WebGL context loss 和 CPU 回退。浏览器与 Tauri WebView 均需验收。
5. 晋级条件：视觉达到每效果预先声明的容差且无语义错序；完整场景 P95 与内存确有收益；CPU 回退可接受。若只快在隔离 shader 而完整 `renderTo` 未改善，则不迁入。网点在单元 2 的覆盖偏差消除前不得晋级。

此实验方案不会自动使对象效果 GPU 化，也不会自动放宽时间轴 Step/Linear 白名单。两者分别需要对象胶囊管线与时序语义验证。

## 杂色斜纹受控诊断与共享效果链（2026-10-13）

### 杂色抖动：已定位为原型随机数源

运行 `node tools/tests/browser/v4-gpu-noise-diagnostic.mjs`。照片与纯灰输入都比较四列：正式 CPU xorshift、原 GPU `fract(sin(dot(...))*43758.5453)`、将输入坐标限制到 8×8 的 GPU 浮点哈希、以及复用 CPU xorshift 字节的 GPU 噪声纹理。除随机数源外，强度 18%、单色、尺寸 1、种子 7、颜色加法公式不变。

| 输入 | 原 GPU 浮点哈希 RGB 误差 | 限幅浮点哈希 | 缓存 CPU 随机纹理 |
| --- | ---: | ---: | ---: |
| 照片 | 31.508 / 255 | 30.361 / 255 | **0.019 / 255** |
| 纯灰 | 32.752 / 255 | 31.438 / 255 | **0.020 / 255** |

### 共享 WebGL 场景后处理原型

本轮尚未覆盖：完整 `renderTo` 与动态对象场景、透明素材／蒙版、场景过渡、随机纹理每 tick 更新、Shader 冷启动、浏览器与 Tauri 双宿主、GPU 计时查询、context loss、CPU 回退、独立 HTML 导出一致性。**生产 Runtime 和文件格式未改。**下一步需把共享管线作为可选择的场景末端路径接入上述完整帧夹具，再决定是否正式采用；对象级可调顺序另设胶囊试验，不能用本场景结果外推。

## 引用来源显示语义：不是 GPU 的硬要求

`sourceVisibility:'keep'|'mask-only'` 是现有项目／编辑器的可见性选择，不是 WebGL 的要求。前述引用蒙版首次对照失败，是因为 GPU 路线的基础画面删除了场景效果配置，连带删除了 `mask-only` 引用；正式 Runtime 的 `maskOnlySources(scene)` 于是把来源画了出来。两条路线使用相同引用关系后，对照通过。GPU 只要求**底图中来源是否显示**与**蒙版纹理中来源 Alpha 是否参与**分别明确，且 CPU/GPU 两条路线一致。

现已按产品决定取消“来源显示”选项，固定为“被引用的元素／组仅作蒙版”，从引用关系派生可见性，不改来源对象自身 `hidden`。同一图片若既要可见又要充当蒙版，可以新建共享素材的可见对象实例；不需要复制图片字节。解除最后一个引用后，来源自动重新显示。对象、组后代、场景效果范围、编辑器预览、保存导出和 GPU 基础画面共用同一派生规则。生产 schema/UI/Runtime 已更新，不兼容旧 `sourceVisibility` 字段。

现有 `maskOnlySources` 扫描所有引用配置，未按效果 `enabled` 或时段启用状态过滤。若固定“仅作蒙版”，需要先明确“已指定引用即保留为蒙版资源”还是“只在效果生效时隐藏”；建议前者，避免来源在效果时段边界突然出现，禁用效果但保留引用时结构树应清楚提示其占用状态。也要验证组后代、多重引用、解除引用及被引用来源自身的动态帧。

| 64 | 16.6 / 19.3 | 1.4 / 2.3 | 17.9 | 56.5 | 11.8 |

对照的平均 RGB 差为 **0/255**，WebGL 无错误且上下文未丢失。此处 GPU 能加速的是**像素映射**，并没有让动态源的调色板提取变便宜；把每帧自动提色称为“纯 GPU 颜色映射”会误导。合理的进一步方案是静态来源缓存调色板、动态来源降低提色刷新率或固定调色板，并另测画质。表中 1–3 ms 仍是 `gl.finish()` 包围的浏览器墙钟，不是 GPU timer query。

### 补测：1080p 低分辨率处理＋独立放大

运行 `node tools/tests/browser/v4-gpu-uneven-two-pass-benchmark.mjs`。同一动态透明椭圆先用 Canvas2D 缩到 640×360；比较 A：全分辨率每像素重复计算动态场／边缘保护／不均取样，和 B：仅在 640×360 计算一次，再以最近邻单独放大到 1920×1080。两条路线都在每帧上传来源；GPU query 包含上传与两道绘制，但**不包含 Canvas2D 来源构图和缩小**，后者包含在单独的主线程计时中。每条件预热 8 帧、采样 40 帧，使用 `EXT_disjoint_timer_query_webgl2`。本机 Edge / Intel UHD 620 三次运行中最后一次：

| 边缘规则 | 全分辨率重复计算 GPU P95 | 低分辨率处理＋放大 GPU P95 | 双道主线程 P95 | RAF 间隔中位 |
|---|---:|---:|---:|---:|
| 关闭 | 12.57 ms | **1.56 ms** | 0.5 ms | 16.7 ms |
| 保护轮廓 | 10.15 ms | **1.93 ms** | 0.5 ms | 16.7 ms |

同一最终帧的两条路线在 RGB、Alpha 上逐像素完全一致；画面非空（可见像素 35.33%），保护轮廓确实改变 0.299% 的输出像素。两次前置运行的双道 P95：关闭 1.38／1.57 ms，保护轮廓 1.68／1.81 ms；均无 disjoint 或 WebGL 错误。这是本轮最强的**单效果 GPU 实验候选**，也说明先前在全分辨率逐像素重算的 19～37 ms 不是不均采样不可 GPU 化的固有成本。注意前节 1080p 测试与本测试的来源上传尺寸和 shader 实现不同，不能把二者数值直接配对计算加速比；本表的 A/B 才是同一输入和同一脚本的对照。

仍不能直接切换正式 Runtime：本夹具只有动态波场、采样尺寸 3、关闭／保护轮廓、单效果；未测噪声场、保护内部、其他尺寸、场景效果范围蒙版、效果链、双 Scene 过渡及导出／Tauri WebView。没有 CPU→GPU→CPU 读回成本；输入仍经 Canvas2D 构图与缩小。下一道门槛是将双道算子放入共享场景 GPU 链，验证与蒙版及相邻效果合成的顺序、全帧预算和纹理峰值，再决定生产接线，而不是仅凭孤立 1～2 ms 数字替换正式 CPU 路径。

### 补测：不均采样＋动态范围蒙版＋后续染色的场景链

运行 `node tools/tests/browser/v4-gpu-uneven-two-pass-benchmark.mjs --scene-chain`。同一 1920×1080 动态透明场景，在不均采样之后以逐帧变化的椭圆范围蒙版合成回原画，再执行染色叠加。GPU 链在同一 WebGL2 上下文中进行；每帧上传全分辨率原画与蒙版、低分辨率采样工作图。GPU query 包括三次上传、取样、放大、范围合成及染色，不包括 Canvas2D 绘制原画／蒙版和缩小输入；后者计入单列主线程耗时。一次本机结果如下，40 个有效 GPU query／条件，无 disjoint 或 WebGL 错误：

| 不均采样边缘规则 | 全分辨率重复计算 GPU P95 | 双道场景链 GPU P95 | 双道主线程 P95 | 双道 RAF 间隔中位 |
|---|---:|---:|---:|---:|
| 关闭 | 15.35 ms | **4.90 ms** | 1.2 ms | 16.6 ms |
| 保护轮廓 | 11.41 ms | **5.00 ms** | 0.6 ms | 16.7 ms |

双道与同链的单道 GPU 输出逐像素一致，范围蒙版及边缘规则都确实改变了画面。进一步与**正式 CPU Runtime** 对照：不均采样效果本身在两种模式的 1080p RGB／Alpha 均逐像素相同；整条链的平均 RGB 差分别为 0.0534／0.0533（满值 255），平均 Alpha 差均约 0.0002。可见像素中通道差超过 2 的占比为 0.0828%／0.0776%；两侧高度不透明的像素中此比例低于 0.001%。其余差异集中在 Canvas2D 与 shader 的半透明颜色合成取整，不能把“整条链逐像素完全一致”写为结论。曾出现的较大不均采样偏差源于夹具将 GPU 和 CPU 的**时间相位对错**，已修正并设画质断言；并非正式 Runtime 的故障。

本夹具按六张显式工作纹理估算场景链离屏 RGBA8 约 **33.4 MiB**，另有默认绘制缓冲、Canvas2D 原画／蒙版和驱动内部副本；这不是实际显存峰值。结果支持双道不均采样进入共享 GPU 场景管线的下一轮候选，但仍不足以直接接入产品：需补测噪声场与保护内部、多张范围蒙版、完整场景效果顺序、两侧动态 Scene 过渡、较低端设备及 Tauri WebView，并避免为每个效果重复上传整帧。

### 补测：两张动态范围蒙版与双 Scene 淡入淡出

同一脚本追加 `--scene-chain --two-masks`：不均采样范围蒙版与染色叠加范围蒙版分别动态变化，每卡独立合成，不能在链末只套同一张蒙版。单 Scene 1080p 双道 GPU P95 在本机约 **6.4–6.6 ms**，两条 GPU 路线输出逐像素相同；不均采样核心与正式 Runtime 逐像素相同，最终平均 RGB 差约 **0.022/255**、Alpha 差为 0。显式离屏纹理估算升至 **49.22 MiB**，未计默认缓冲／Canvas2D／驱动副本。

再追加 `--dual-scene`：每帧让上一场景与当前场景各自更新原画、采样场及两张范围蒙版，各自运行完整效果链，最后在同一 WebGL2 上下文中按正式 `fade` 的“当前画面先绘、上一画面按剩余比例覆盖”语义合成。两侧确实随时钟变化：相邻帧上一／当前 Scene 的平均 RGB 变化约 **1.54／0.35**；与正式 CPU Runtime 合成后的平均 RGB 差 **0.0327～0.0328/255**、Alpha 差约 **0.0002/255**。双道与全分辨率单道 GPU 的最终画面逐像素相同。一次 40 帧运行：

| 边缘规则 | 双 Scene 单道 GPU P95 | 双 Scene 双道 GPU P95 | 双道主线程 P95 | 双道 RAF 间隔中位／P95 |
|---|---:|---:|---:|---:|
| 关闭 | 27.74 ms | **15.35 ms** | 3.3 ms | 16.7／33.3 ms |
| 保护轮廓 | 27.22 ms | **16.09 ms** | 3.8 ms | 16.7／33.2 ms |

GPU query 已包含两侧各自的来源／双蒙版上传、各自效果链、两次场景画面的 GPU 内复制和最终淡入淡出；不含 Canvas2D 构图。可读取样本双道 39、单道 37，未报告 disjoint 或 WebGL 错误。显式离屏纹理估算 **65.04 MiB**，仍非显存峰值。结论应分开：**时序与画质语义通过这一组 fade 参数的实验；性能尚不满足稳态 60 fps 的充足余量**。RAF P95 已出现 33 ms，且产品还要承载编辑器 UI、其他卡片和素材准备。30 fps 可能更现实，但须在正式播放器与 Tauri WebView 重测，不应由隔离夹具直接承诺。后续优先减少每 Scene 的全尺寸蒙版纹理／上传与不必要的全尺寸中间画面，并补测 wipe／dissolve、噪声场、不同画布和完整效果顺序。

### 优化实验：融合范围合成／染色，直接输出双 Scene 纹理

追加 `--fused`，在原单道、双道旁增加第三条路线：低分辨率不均采样保持独立；放大、第一张范围蒙版合成、染色、第二张范围蒙版合成融合到一次全尺寸 shader。中间位置保留 RGBA8 量化，限制融合导致的颜色差；上一／当前 Scene 直接写入各自纹理，取消从默认 framebuffer 复制场景画面的两次 `copyTexSubImage2D`。因此每 Scene 从五次绘制减为两次，双 Scene 加转场从十一次减为五次。对象绘制、蒙版的 Canvas2D 生成、原画与蒙版上传仍使用前轮方法。

运行：

```text
node tools/tests/browser/v4-gpu-uneven-two-pass-benchmark.mjs --scene-chain --two-masks --dual-scene --fused
node tools/tests/browser/v4-gpu-uneven-two-pass-benchmark.mjs --scene-chain --two-masks --dual-scene --fused --transition=wipe
node tools/tests/browser/v4-gpu-uneven-two-pass-benchmark.mjs --scene-chain --two-masks --dual-scene --fused --transition=dissolve
```

三种转场均在同一脚本内比较单道、双道和融合路线；1920×1080、采样尺寸 3、逐帧变化的两侧场景和各两张范围蒙版。转场进度固定为 0.45；擦除采用向右，溶解采用颗粒尺寸 16、随机种子 9。溶解 shader 复用正式 Runtime 的 uint32 哈希公式，CPU 对照直接调用正式 `renderer.drawTransition`，不另写近似的 CPU 转场规则。下面每个区间分别涵盖“关闭／保护轮廓”两种边缘规则，单位 ms：

| 转场 | 同轮双道 GPU P95 | 融合 GPU P95 | 融合主线程 P95 | 融合 RAF 间隔 P95 | 与正式 Runtime 平均 RGB 差 /255 |
|---|---:|---:|---:|---:|---:|
| 淡入淡出 | 17.82–18.04 | **12.60–12.81** | 2.4–3.7 | 16.7–16.8 | 0.0416–0.0418 |
| 向右擦除 | 17.52–19.12 | **13.54–13.77** | 2.6–3.0 | 16.8–33.3 | 0.0259–0.0260 |
| 溶解 | 18.37–19.60 | **12.58–13.66** | 3.1–4.0 | 16.7–33.3 | 0.0293–0.0295 |

融合与分步双道的平均 RGB 差为 0.0078–0.0094/255，平均 Alpha 差均为 0；与正式 Runtime 的平均 Alpha 差不超过 0.0002/255。两侧的相邻帧均变化，未冻结；无 WebGL 错误或 disjoint。shader 融合没有达到逐像素完全相同，但该组画面、范围和参数通过夹具的画质断言。

**资源统计须区分分配与使用。** 该 A/B/C 夹具为了同时保留三条路线，仍分配旧路线的全部纹理，显式分配量为 65.04 MiB；融合路线实际需要的工作纹理集合估算为 **41.31 MiB**（少三张全尺寸 RGBA8，共 23.73 MiB）。本轮没有测出实际显存峰值下降，也没有证明驱动回收／WebView 的实际内存开销；正式接线时须仅按实际路线分配。

**本轮结论：** 减少全尺寸中间图和场景复制有效，场景处理链应按可融合的连续计算组织，而非为每张卡固定创建一套 Canvas／GPU 来回路径。融合改善了本机双 Scene 的 GPU 时间与帧节奏，但擦除／溶解仍出现 33 ms 尾帧；完整作品与编辑器稳定 60 fps 仍未通过。正式 Runtime、导出和 Tauri 尚未切换。下一步优先在只分配融合所需资源的原型中验证 GPU 端缩小输入、减少上传和长时运行，再补全过渡进度／方向、采样格与场类型的覆盖，后续才能制定生产场景 GPU 执行器的接线合同。

### 连续验证：只分配融合资源，比较 Canvas 与 GPU 缩小输入

新增 `--fused-only`，独立运行融合路线，仅创建 7 张工作纹理，实际显式 RGBA8 分配为 **41.31 MiB**；不再为了保留 A/B 对照而分配 65.04 MiB。新增 `--gpu-downsample`，复用已上传的全尺寸原画，在 GPU 上缩小为 640×360，再进入不均采样。两侧 Scene 合计每帧来源／蒙版上传从 **8 次降到 6 次**，省去 Canvas2D 缩小与低分辨率图片上传，但多两次低分辨率 GPU 绘制。纹理在初始化时分配，播放过程中计数保持不变。

```text
node tools/tests/browser/v4-gpu-uneven-two-pass-benchmark.mjs --scene-chain --two-masks --dual-scene --fused-only --frames=1800
node tools/tests/browser/v4-gpu-uneven-two-pass-benchmark.mjs --scene-chain --two-masks --dual-scene --fused-only --gpu-downsample --frames=1800
```

每条路线分别在关闭／保护轮廓模式连续播放 1800 帧，约 30 秒／模式，按前／中／后三段记录耗时。两条路线各自有效 GPU query 1792／模式，无 disjoint、WebGL 错误或上下文丢失，播放期间新增纹理数为 0。本机结果：

| 缩小位置 | 边缘规则 | GPU query 中位／P95 | 主线程中位／P95 | RAF P95 | 帧间隔超过 25 ms |
|---|---|---:|---:|---:|---:|
| Canvas2D | 关闭 | 11.01／12.63 ms | 1.7／2.8 ms | 33.2 ms | 5.97% |
| Canvas2D | 保护轮廓 | 11.04／12.32 ms | 1.9／12.3 ms | 30.8 ms | 6.19% |
| GPU | 关闭 | 11.63／13.34 ms | 1.5／2.8 ms | 33.2 ms | 5.80% |
| GPU | 保护轮廓 | 11.46／12.74 ms | 1.4／2.4 ms | 16.9 ms | 3.01% |

GPU query P95 在前／中／后三段未持续恶化：Canvas 关闭 13.32／12.11／12.51 ms，保护轮廓 12.27／12.19／12.44 ms；GPU 关闭 14.06／12.83／13.01 ms，保护轮廓 12.77／12.52／12.82 ms。Canvas 保护轮廓组的主线程尾部出现明显尖峰，GPU 缩小组更平稳；单次顺序执行受浏览器调度及设备负载影响，尚不能据此判定尖峰一定由 Canvas 缩小引起，也不能把“零新增纹理”推断为浏览器／驱动不存在任何内存增长。

两种缩小路径在本组最终固定时刻与正式 Runtime 的平均 RGB 差相同（0.0366／0.0367/255），Alpha 差均约 0.0002/255；两侧场景相邻帧都变化。GPU 缩小没有新增这组画面的视觉误差，但 GPU query 中位与 P95 略高，因此**上传次数减少并不等于总 GPU 成本下降**。当前保留两条路线为原型选项，生产默认策略尚未确定。边缘保护关闭组仍约 6% 的帧间隔超过 25 ms，稳定 60 fps 未通过；30 fps、正式 Player、Tauri WebView、不同采样尺寸与来源素材仍需独立验收。

此轮完成了低分辨率处理、双蒙版、双 Scene 的资源复用和一段连续运行验证。接下来应先建立场景 GPU 执行器的资源／上传／回退合同，将源版本、尺寸与蒙版版本作为更新依据，明确静态内容何时免上传，再验证完整效果链与无 WebGL 回退。继续增加孤立 shader 的收益已低于验证真实 Player 接线与缓存生命周期。

### 真实 Player 第一条实验接线（2026-10-14）

已加入 `69a-scene-gpu-executor.js`，并让正式 `createRuntime().renderTo()` 通过绘制选项 `sceneBackend:'gpu-experimental'` 显式尝试。默认编辑器／导出场景路径维持 CPU；既有 CRT 行为维持原样。能力／资源／版本／回退边界详见 [V4_SCENE_GPU_EXECUTOR_CONTRACT.md](./V4_SCENE_GPU_EXECUTOR_CONTRACT.md)。当前只接独立采样格与不均采样及其范围蒙版，其他启用效果触发整条 CPU 场景链回退；这不是全部效果迁移完成。

接线审查确认生产场景固定为 `overlay → sample`；前面部分隔离组合测试的 `sample → overlay` 只能证明那组顺序的算子可行，不能直接作为生产整链等效依据。真实 Player 的最终转场仍交给 Canvas2D；GPU 双源最终合成的隔离性能也不能直接当作该 Player 的完整帧成本。

`node tools/tests/browser/v4-gpu-player-lifecycle.mjs` 定向测试：

- 12 组固定画面对照，覆盖波／径向／噪声场、采样格 1／3／4、333×187 非整除画布、矩形／椭圆／Alpha／动态引用元素蒙版及反相；平均 RGB 误差最大 **0.0789/255**，Alpha 最大 **0.0181/255**。
- Step 同时改变采样尺寸、场类型与参数的两段画面均逐像素一致。初测曾出现噪声段偏差；uint32 哈希实测相同，改用精确整数除法划分噪声格与采样单元后偏差消失。非整数噪声场尺度暂回退 CPU，不限制 Inspector 原值。
- 暂停且调用方来源版本不变时，缓存命中，新增上传／GPU pass 均为 0；参数修改、撤销、seek 或版本缺失均刷新。撤销后的画面与修改前逐像素相同。
- 同尺寸连续绘制只初始化一个上下文、四张工作纹理；改变来源尺寸会先释放旧资源，再创建新尺寸资源。独立 Player B 释放后 A 的画面与缓存仍正确。
- 模拟 WebGL 不可用、上下文丢失和加入不支持的染色卡，均完整回退 CPU；Alpha 与 CPU 基线一致，预乘 RGB 比较一致，原始直通 RGB 有小于 0.014/255 的低 Alpha 反量化差。清缓存后可重新建立 GPU 路线。
- 双 Scene 连续转场只使用一个 GPU 上下文；内部上一 Scene 离屏复用累计为 0 → 2 → 4，不再每帧创建全新 Runtime。三处转场时刻与 CPU 基线逐像素相同；修改上一 Scene 的背景后也保持一致。

除实验 GPU 接线外，正式默认 CPU 转场也采用缓存的上一 Scene Player，两侧共享活的规范化场景数据。既有 `v4-gpu-alpha-mask-order-transition.mjs` 透明度、蒙版、可调对象阶段与 fade／wipe／dissolve／blackout 定向回归通过；Runtime smoke、Scene／Adapter 合同和分发镜像一致性检查通过。一次性公共 `renderTo` 在返回画面后自动释放临时 Player，GPU 画面保留且上下文释放已单独验收。当前测试证明接线正确性和回退机制，不提供真实 Player 的全帧 GPU 性能结论，也不代替全量编辑器 UI 回归；性能与 Tauri／导出后端自动选择仍待下一轮。

### 真实 Player 完整帧首轮预算（2026-10-14）

新增 `tests/browser/v4-gpu-player-performance.mjs`，直接调用正式 `createRuntime/renderTo`，不加载编辑器 UI。来源为 karsten 照片与八个动画矩形；动态范围采用被引用的椭圆对象，按正式 resolver 隐藏来源并生成蒙版。采样尺寸 3，不均采样波场带流动／潮汐，场景背景不透明。双 Scene 使用动态两侧画面与淡入淡出，最终合成仍为 Canvas2D。此轮不覆盖其他场类型、多效果整链、透明最终背景、其他转场、Tauri 或 Inspector 操作成本。

```text
node tools/tests/browser/v4-gpu-player-performance.mjs --write-report
```

本机 Edge／ANGLE Intel UHD 620 D3D11，每路线先预热 8 帧，再记录 64 帧；每尺寸按单场景、动态范围、双场景动态范围测试 CPU 与实验 GPU。固定时刻画质读取在计时之外，播放循环没有 `getImageData`。原始结果保存在 [v4-gpu-player-performance-result.json](v4-gpu-player-performance-result.json)。单位 ms：

| 尺寸／工作负载 | CPU 主线程 P95 | GPU 路线主线程 P95 | CPU RAF P95 | GPU 路线 RAF P95 | GPU 上下文 query P95 |
|---|---:|---:|---:|---:|---:|
| 640×360 单 Scene | 14.1 | 4.2 | 16.7 | 16.7 | 14.56 |
| 640×360 动态范围 | 13.0 | 4.8 | 16.8 | 16.8 | 13.51 |
| 640×360 双 Scene 动态范围 | 26.4 | 8.8 | 33.3 | 16.7 | 11.79 |
| 1920×1080 单 Scene | 46.0 | 5.1 | 50.0 | 16.8 | 10.71 |
| 1920×1080 动态范围 | 54.1 | 15.0 | 51.1 | 16.7 | 9.13 |
| 1920×1080 双 Scene 动态范围 | 94.2 | 26.0 | 100.0 | 33.3 | 7.70 |

**读数边界：** 主线程计时包围完整 `renderTo`，包含对象绘制、来源准备、上传提交、GPU 结果交给 Canvas2D 与最终转场；它不是仅 shader 提交时间。GPU query 从同一 WebGL 上下文包围 Player 调用，包含该上下文的执行与可能的依赖／调度等待，不包含所有 Canvas2D 设备工作；主线程与设备并行，两项不能相加当作完整帧耗时。较大工作负载出现较低 query，也不能推断其 shader 更快。RAF 衡量实际调度节奏，但 64 帧短测没有证明长期稳定或浏览器呈现帧率。

GPU 路线 1080p 单 Scene 超过 25 ms 的 RAF 间隔为 0%，动态范围为 1.59%，双 Scene 为 31.75%；双 Scene 最大 RAF 间隔 99.9 ms。CPU 组也有 149–749 ms 的间隔离群值，不能用 P95 抹掉这些尖峰，初始化、浏览器调度、GC／驱动等原因尚未逐项定位。此轮为一次顺序运行，不用于跨设备保证。

所有 GPU 组有效 query 均为 64，无 disjoint／WebGL 错误。预热后新增纹理数和 backing size 写入均为 0，每个 Player 只建一个 GPU 上下文；显式纹理 640×360 为 1.95 MiB、1080p 为 17.58 MiB，不含 Canvas2D 离屏／驱动资源。每帧单 Scene 无范围上传 1 次／处理 2 道；动态范围上传 3 次／处理 2 道；双 Scene 动态范围合计上传 6 次／处理 4 道。真实 Player 统计现已汇总两侧，内部上一 Scene 的离屏复用持续增加。

六组固定时刻比较的平均 RGB 误差最大 0.0009/255，Alpha 差均为 0（本夹具最终背景不透明）；单 Scene 无蒙版逐像素一致。正确性／生命周期测试另覆盖透明画面，不能用本轮 Alpha 为 0 推断全部透明路径已验证。

**结论及下一步：** 首条真实接线确实降低本机主线程成本、改善实际帧节奏，收益并非只有隔离 shader。1080p 双 Scene 仍明显超过 60 fps 单帧预算，不均采样 shader 之外的来源绘制／动态蒙版准备／GPU→Canvas2D 输出／最终 CPU 转场需进一步分项定位；当前尚不能将成本精确归因某一项。下一步应验证同 GPU 上下文保留两侧输出并完成转场融合，然后按生产 `overlay → sample` 扩大真实整链、重复／长时测试与宿主生命周期。默认 CPU、白名单外整链回退、项目格式和 UI 均维持不变。

### 真实 Player 同上下文双源最终转场（2026-10-14）

新绘制选项 `sceneGpuTransitions:true`（须同时指定实验 GPU 场景后端）将当前／上一 Scene 输出直接写入两张全尺寸 RGBA8 纹理，最终 fade／四向 wipe／dissolve 在同一上下文合成，一次输出到 Canvas。两侧独立运行时钟、源对象绘制、动态蒙版准备和上传仍按正式 Player 执行。常规单 Scene 四张纹理不变；首次 GPU 转场惰性增至六张，之后复用。不同采样工作尺寸／白名单外链／黑场继续 Canvas 最终转场；发生 GPU 输出或合成错误则完整重绘当帧 CPU，不以旧 GPU 帧作为补偿。

`v4-gpu-player-lifecycle.mjs --write-report` 扩充透明场景、333×187 非整除尺寸、淡入淡出、四向擦除、溶解、进入／离开／回到转场时刻、动态两侧、修改上一背景和模拟最终合成失败，以及默认关闭／不同采样尺寸／黑场回退。透明固定时刻平均直通 RGB 最大差 **0.4307/255**、平均 Alpha 最大差 **0.003/255**、预乘通道最大差 **2/255**；减少中间 Canvas 往返会改变量化，并非逐像素完全相同。对比阈值明确为透明直通平均 RGB <0.5、Alpha <0.1、预乘最大差 ≤2，而原单 Scene 测试阈值未放宽。seek 对照也记录 CPU 同时刻重复绘制的微差，不将低 Alpha 反量化差误称为陈旧纹理。模拟合成失败的完整 CPU 重绘逐像素一致。证据为 [转场正确性 JSON](v4-gpu-player-transition-correctness-result.json)。

在同版本同设备顺序运行两条实际 Player 基准（均每组预热 8、记录 64 帧），不是隔离转场 shader 测试：

```text
node tools/tests/browser/v4-gpu-player-performance.mjs --canvas-transition --write-report
```

下面两侧均有不均采样和动态引用范围，单位 ms；GPU query 的边界与上一节一致，不是全部 Canvas2D＋WebGL 的设备时间。

| 尺寸／最终合成 | 主线程 P95 | RAF P95 | >25 ms 间隔 | WebGL query P95 | 显式工作纹理 |
|---|---:|---:|---:|---:|---:|
| 640×360 Canvas | 9.1 | 16.7 | 0% | 11.42 | 1.95 MiB |

**结论：接线可行，但首轮完整帧没有体现提速，纹理占用显著上升。** 因此 `sceneGpuTransitions` 默认关闭，不更换编辑器或导出默认路径，也不推断同上下文 GPU 转场在所有作品都无益。来源绘制、Canvas 缩小、动态引用蒙版生成与六次上传尚未消除，省掉最终 Canvas 合成不足以解决本组瓶颈。下一轮优先进行这些过程的分项计时，再决定 GPU 缩小输入、范围缓存或其他措施；不能仅由主线程／query 比例归因，也不应继续盲目增加 shader 融合。

### 主线程分项与同步等待定位（2026-10-15）

嵌套 API 验证：缓存前 `checkFramebufferStatus` 中位 12.4 ms／P95 17.2 ms，缓存后播放测量阶段不再调用；`getError` 从 1.9／2.8 ms 转为 13.9／20.3 ms。GPU 提交阶段下降不是完整帧相同比例提速，主要是等待位置发生变化。两次顺序短测不能证明 P95 的 1.7 ms 差异显著，缓存后 RAF P95 仍 33.4 ms、超过 25 ms 间隔 31.75%，未通过稳定 60 fps。单场景无范围中位 3.9→2.9 ms 但 P95 4.8→4.9 ms；有范围中位 7.0→6.3 ms、P95 14.7→15.1 ms，也不构成尾帧提升结论。

**机制判断是推断，不是完整 GPU 因果证明：** 查询会等待前面的上传／GPU 绘制及跨 Canvas 来源依赖完成，因此主线程时间集中在查询处，不能认为 framebuffer 完整性计算本身需要十几毫秒。去掉前一个同步点会把等待移到下一个；来源绘制／上传 API 返回快，也不能证明该阶段的设备工作已完成或成本低。尚未逐阶段测出上传依赖、shader 和驱动调度各占多少。

附件纹理存储与尺寸在一个执行器代际内固定，现仅首次绑定时验证完整性；尺寸重建／新转场附件重新验证。逐帧 `getError`、上下文丢失检查、不支持链预检与完整 CPU 回退没有取消。计时开关前后画质、普通绘制不暴露诊断字段、固定资源无重复附件查询以及模拟不完整 framebuffer 回退由生命周期测试覆盖。三次性能诊断的固定画质误差仍 ≤0.0009/255、Alpha 为 0，资源复用断言通过。

下一步必须进一步测 WebGL 内上传／绘制阶段的设备时间，再用实验选项验证不阻塞主线程的提交／错误验证节奏及可靠回退。不得仅删除错误检查来声称提速，也不能将错误晚发现的风险带进默认编辑器。对象来源仍是 Canvas2D，本轮不涉及重写对象渲染器、扩大 GPU 效果白名单或改变导出／UI。

染色48组照片、色散24组、临界灰阶、CSS与动态、Linear实际颜色／Alpha变化、Step／seek与色散故障回退均通过，本组输出逐像素一致；旧杂色96组严格透明及阈值／生命周期继续通过。五卡无范围15道、独立范围20道、双侧范围转场41道，预热后上传1／6／12次。1080p同次CPU/GPU P95为168.0/18.7、198.0/43.5、403.8/81.6ms，显式GPU纹理41.56/57.38MiB（单/双Scene）；双侧明显不稳定30fps。默认CPU、UI与格式不变，连续染色动画性能及其他混合模式仍待测／接入。详见[五卡实现与预算](V4_GPU_TINT_DISPERSION_PLAYER_2026-10-15.md)。
