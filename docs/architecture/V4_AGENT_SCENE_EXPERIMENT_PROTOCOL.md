# v4 Agent 场景实验协议

状态：**C1 已通过工程 + 基础创作门槛；C2-B 语义照片分层已通过首轮工程验证；C3 待执行。**

本协议用于验证 ToSampool v4 的 Agent 协作能力，不把三张好看的示例误当作通用能力证明。它将创作案例、工程控制组、可变工作流与评价证据分开记录，使一次失败能够归因于提示、载体选择、Runtime 或人工补丁中的某一项。

相关边界：

- [Scene Module 协议](V4_AGENT_SCENE_MODULE_PROTOCOL.md)：复杂程序绘制可作为项目 Module，不强迫拆成低层图元。
- [v4 Scene 合同](VNEXT_SCENE_CONTRACT.md)：Agent 输出必须遵守的工程格式与运行时边界。
- [项目会话隔离](V4_PROJECT_SESSION_ISOLATION.md)：实验项目不会污染后续项目或同页 Player。
- [Draft Package 与执行计划](V4_AGENT_DRAFT_PACKAGE_PLAN.md)：Agent 实验、Browser Bridge 与未来 Tauri Host 共用的草稿包和分阶段边界。
- [Agent Context Pack](V4_AGENT_CONTEXT_PACK_PROTOCOL.md)：隔离 Agent 接收的能力地图、载体策略与质量门槛。
- [创作方向协议](V4_AGENT_CREATIVE_DIRECTION_PROTOCOL.md)：从方向卡冻结的构图不变量、节拍、禁止项和视觉自检点。

## 1. 实验目标

验证的不是“Agent 是否能生成一张漂亮图”，而是以下命题：

> Agent 能否依据输入来源与视觉意图，选择足够诚实、轻量且可继续编辑的 Scene 载体，并使人类能接手修改。

“诚实”指 Scene 明确表达主要画面是来源图片、程序 Module、普通对象，或它们的组合；不能把整张完成画面塞进背景后仍宣称主要内容可编辑。

## 2. 案例与覆盖面

三类案例覆盖用户常见的输入条件，但不再对应三条产品工作流。C1 与 C3 是统一 `scene-author` 的两种评测配置；C2 是独立 `asset-derive` 流程。

| 编号 | 案例 | 用户输入 | 核心验证 | 不可接受的捷径 |
| --- | --- | --- | --- | --- |
| C1 | 空白基底创作 | `scene-author / base=blank` + 自然语言 + 可选参考图 | 从零建立可编辑循环场景；由用户确认结构优先、素材优先或混合载体 | 禁止生图，迫使所有细节降级为粗糙图元；或用一张完成图冒充完整结构 |
| C2 | 从图片拆素材 | 至少一张源参考图 | 语义拆分、Alpha 审阅、底层补全与可选多帧变体 | 未经审阅直接入库；或继续追加简单动效并冒充完整场景成果 |
| C3 | 所选素材基底创作 | `scene-author / base=selected-assets` + 用户确认素材 + 可选参考图 | 素材角色、空间组织、程序补件、公开参数与循环节奏 | 自动网格排版，或只把素材叠放而没有构图判断 |

另增协作修订组 C4：`scene-author / base=current-scene / scope=selection|scene`。输入是人类已完成一部分的真实工程，重点验证 Agent 是否理解当前画面、保持稳定 ID、只修改授权范围并避免重复素材。C4 是“共同创作”成立的必要证据，不是第四条产品入口。

三例之外保留两个不对外宣传的控制组：

| 编号 | 控制组 | 用途 |
| --- | --- | --- |
| K1 | Runtime 校准场景 | 固定的小型对象、Module、时序、蒙版、采样和导出场景；确认问题不是 Runtime 回归 |
| K2 | 载体策略对照 | 对同一输入分别采用“整图背景”“语义分层”“原生/Module”路线；测量视觉、可编辑性、体积与性能的取舍 |

## 3. 实验变量

### 3.1 固定项

每轮必须冻结并写入报告：

- v4 Runtime、编辑器提交版本和 Agent Skill 版本；
- 模型、推理档位、可调用工具和模型侧随机性设置；
- 画布尺寸、循环时长、目标帧率、预览预算及导出形式；
- 用户提供素材、许可状态与原始提示；
- 性能采集方法：固定时间点、同一设备、同一 Preview 档位。

第一轮不为某一案例即时改 Runtime。发现 Runtime 缺口时记录为阻塞项，另开修复轮后从头复测该案例。

### 3.2 主变量：Agent 协议

提示词和 Skill 是第一轮主要被优化的变量。协议分四层，后续只改变其中一层并保留其它层：

1. **任务层**：叙事、目标风格、时长、必须保留的主体。
2. **载体层**：允许与禁止的承载方式；要求 Agent 解释为何选择背景、图片层、原生对象或 Module。
3. **编辑层**：至少列出公开参数、可独立修改对象和预期人类补丁位置。
4. **自检层**：结构校验、固定时间渲染、性能预算、载体组成报告。

### 3.3 受控选择结果：载体策略

下列不是同一变量的混合名称，必须分别记录：

| 决策 | 选项 |
| --- | --- |
| 视觉素材来源 | 用户图 / Agent 生成图 / 程序绘制 / 用户多素材 |
| 工程载体 | 原生对象与图元 / 项目 Scene Module / 图片层或背景 / 混合 |
| 编辑粒度 | 对象变换与效果 / Module Manifest 参数 / 背景上附着补丁 |

“先生图再模仿”必须拆成“是否生成图”和“该图以何载体进入 Scene”两条记录，不能笼统算作 Agent 生成能力。

## 4. 案例路线

### C1：文本雪花球

候选路线：原生对象为主；复杂、静态但高细节的部分可使用项目 Module；不得默认使用一张生成背景作为最终答案。重点测 Agent 能否选择可编辑的季节段、主体、粒子和转场公开参数。

首轮 C1 的比较顺序固定为：

1. **C1-A / 原生下限**：图元与粒子，不允许 Module；确认纯声明式工程至少能完整交付。
2. **C1-B / Module 无脚手架**：允许 Module、只给能力地图；若 Agent 自创项目格式，记录为协议输入失败，不改草稿。
3. **C1-B2 / Module 文件脚手架**：同一 Brief、同一预算，只增加 Context Pack 的 Module 文件模板。结果用于暴露“项目格式正确”与“可运行 Scene 语义正确”之间的差距。
4. **C1-B3 / 完整 Scene 脚手架**：加入经 Runtime smoke 的图元、粒子、显示时段、Scene 转场和 Module 注册范式。结果证明它可交付并渲染，但视觉审阅发现 Module 误用项目绝对坐标、三季 visibility 未明确互斥，因而越界叠绘。
5. **C1-B4 / 局部坐标与互斥可见性**：补充“Module 局部中心坐标”和“非持续对象显式 0..1 visibility 覆盖”的合同，并以静态检查拦截遗漏。工程与 Runtime 均通过（1920×1080 / 36s / P95 7.9ms），但视觉审阅发现“球内景”仍是矩形，需进入创作 Brief 层而非继续修改结构协议。
6. **C1-B5 / 创作方向**：加入“玻璃体积、圆形内景裁切、三层景深、季节焦点与反例”的 Creative Direction 后，内景容器与季节辨识明显改善，工程渲染 P95 4.4ms。但草稿把 `carrier-report.objects` 错写为 `carrierPlan`，且把普通 Scene 实体 `x/y` 误当中心点，导致外层球体、底座和高光错位。该 run 保留为“创作方向有效，但报告与普通实体坐标合同仍需强制”的证据，不人工修补。
7. **C1-B6 / 完整坐标与报告合同**：只新增普通实体左上角坐标规则、载体报告非空校验与实际 entity id 要求；Creative Direction、Runtime、载体类型与性能预算均冻结。结果为 13 实体 / 1 Module / P95 3.9ms：三季内景、玻璃球、底座与高光正确落在同一构图，报告用 10 个真实 entity id 说明冻结与可编辑边界。C1 的“工程 + 基础创作”门槛据此通过；它不宣称已达到高保真生图品质，下一步才应测试不同输入类型与 Agent Skill 的质量上限。
8. **C1-B7 / 语义公开控制**：B6 的 `atmosphere` 只有微弱运动差异，不能算作好的可编辑接口。本轮冻结三项公开参数：动态强度、光色、细节密度，要求 Manifest、Module 绘制和载体报告逐项对齐；`season` 继续作为内部时序参数。结果为 1920×1080 / 36s / 7 实体 / 1 Module / P95 5.6ms，三项控制均有明确像素结果。原始 B6 保留为参数设计反例，B7 不伪装为同一份初始输出。

因此 C1 的下一层不是另一个数据格式：它应向 Agent 提供构图约束、层次和可见性验收（例如“内容必须被球内圆形边界裁切”），让 Agent 在固定的工程合同内完成一次预览—审阅—修订。只有该**创作质量轮**通过结构、Runtime 与人工创作审阅后，才比较 Module 与原生路线的可编辑性、性能和细节；不能把“格式有效”误作“视觉成功”。

### C2：从图片拆素材

C2 验证的是派生素材质量，不再把“分层后继续增加运动、调色和效果”作为完成条件。流程固定为：语义派生计划 → 用户批准 → Alpha/补全候选 → 人工审阅 → 原位复合校验 → 接受项进入素材栏。原位复合是临时校验视图，不保存为正式 Scene。

源图通过“Agent 创作”的共享参考图入口提交并标为 `source`。桥接发送处理后冻结像素，而不是素材路径；详见 [参考图输入协议](V4_AGENT_REFERENCE_INPUT_PROTOCOL.md)。未来 Tauri Host 负责将其写入 run 的 `input/references/`。

首轮 C2-B 使用 `karsten.jpg` 制作三层动态 Scene 的记录保留为早期边界探索，不再代表 C2 的正式交付目标。它暴露的矩形裁切、人物边缘、底层补洞和天空露缝问题，现在统一归入派生素材审阅门禁。

`c2-karsten-transparent-derived-layers` 证明了“冻结原图 → 可审阅透明素材 → 普通图片资产”的工程路线，但其手工坐标遮罩不证明自动语义分割质量。后续 C2 只以素材包、来源关系、非破坏 Alpha、补全质量和独立移动检查为证据；姿态或逐帧序列作为用户显式开启的独立派生任务。具体文件关系见 [派生素材协议](V4_AGENT_DERIVED_ASSET_PROTOCOL.md)。

### C3：粗糙波普拼贴

重点不是完全重绘素材，而是选择、裁切、遮罩、图样、采样与节奏的共同构图。结果需要明确哪些素材是原始输入、哪些是 Agent 生成的补充素材、哪些效果只作用于局部。

## 5. 成功门槛与评分

每例分为“工程通过”与“创作审阅”，不把主观审美伪装成像素级真值。

| 维度 | 工程通过条件 | 记录原因 |
| --- | --- | --- |
| 结构有效 | v4 Scene / Module 校验通过；无浏览器错误；固定时间可重复渲染 | 基础可靠性 |
| 交付一致 | 编辑器预览、`scene.runtime.js`、`scene.embed.html` 在采样时间点一致 | 所见即所得 |
| 载体诚实 | 报告背景、图片、原生对象、Module 的贡献；声明不可编辑部分 | 防止背景偷懒 |
| 可编辑性 | 至少完成五个接手任务：主色、位置、尺寸、运动、局部效果/范围 | 验证人类能继续创作 |
| 性能/体积 | 记录 P95、对象数、离屏像素遍数、素材数、交付体积；不超过该案例预算 | 验证轻量承诺 |
| 人工成本 | 记录人工补丁次数、类型与耗时 | 判断 Skill 的协作价值 |

创作审阅使用 1–5 分，至少包含：任务契合、主体辨识、循环自然、风格一致、可编辑性体感。单图案例可额外评价主体/构图的保真度；纯文本和拼贴不使用像素相似度作为正确性标准。

## 6. 每次运行的最小产物

```text
tools/.local/agent-runs/<run-id>/
├─ run.manifest.json          # case、冻结的 Skill/模型与状态
├─ prompt.md                  # 原始任务、输入素材与协议版本
├─ draft/                     # Agent 唯一允许写入的 Draft Package
│  ├─ project.tosampool.json  # 可编辑工程 Scene 的唯一真相
│  ├─ carrier-report.json     # 载体选择、公开参数、成本、已知限制
│  ├─ assets/                 # 如有，项目级素材副本
│  └─ modules/                # 如有，仅为该项目所需的 Module
├─ evidence/                  # 验证器生成的 metrics 与固定时间帧
└─ review.md                  # 人工接手任务与审阅结论
```

`scene.runtime.js`、`scene.embed.html` 和截图均为**草稿通过验证后**生成的派生产物，不允许 Agent 把它们当编辑真相。只有 `project.tosampool.json`、项目 Module 与用户允许公开的素材可以作为编辑真相。

若 Draft 含有公开的项目 Module 参数，必须额外运行 `scripts/verify-agent-module-controls.mjs --input <draft> --output <evidence/module-controls.json>`。该检查在每个 Module 实体的可见时段，比较参数默认值与替代值的像素哈希；“Inspector 中出现参数但画面不变”的草稿不得进入人工审阅。

## 7. 迭代纪律

1. 每轮只修改一层 Agent 协议，或单独修复一个 Runtime 缺口。
2. 任何“补一张背景图即可”的方案都可作为成本基线，但不能满足 C1/C2 的结构成功条件。
3. 对同一提示至少保留一次未经人工改写的初始结果；人工修改必须单列。
4. 若模型输出具有随机性，保留完整输出和运行编号；需要比较提示时至少重复两次。
5. 结论写为“在此输入、此版本、此预算下”，不外推为普遍 Agent 能力。

## 8. 创作卡实施状态

第一层已在 Classic v4 Shell 实现，入口逐步更名为“Agent 创作”。它是 Agent 之前的稳定用户协议，而不是内嵌模型的替代品。界面必须从一句自然语言开始，不能要求用户先填写一张工单。面板现有两条显式工作流：`起景 / 编排` 产出可审阅的 Scene Draft；`派生素材` 只产出计划卡与透明候选，接受后才进入素材栏。

```text
选择基底与作用域（新场景 / 所选素材 / 当前画布 / 当前选择）
  → 一句话意图（用户）
  → Agent 复述 + 一个会改变结构的追问
  → 用户选择控制程度
  → 方向卡（本地规划或 Agent propose）
  → 用户选择方向
  → Agent build 生成完整、隔离的临时 Scene
  → 用户检查预计变化，再决定应用到当前项目或丢弃
```

- `editor/vnext-agent-creative-protocol.js` 定义 `intent`、`candidate`、分阶段 `response`、能力 Manifest 与本地透明规划器。`intake` 阶段会丢弃方向卡；`directions` 阶段会丢弃追问，避免模型一次返回全部内容破坏渐进交互。
- `editor/vnext-agent-creative-bridge.js` 是可选的浏览器—宿主消息桥。它以 `tosampool-agent-creative-request` / `tosampool-agent-creative-response` 事件交换带 `requestId` 的 `propose`、`build` 请求；不含模型、密钥、网络请求或 Scene 写入。
- `editor/classic-v4-agent-creative-controller.js` 只负责对话、选择卡和安全的临时生成入口，不拥有模型，也不直接写项目。
- 未安装 `ToSampoolV4AgentAdapter` 时，UI 采用本地规划器返回透明的三条方向；它不会伪装成已生成画面，也不会改写当前 Scene。
- 外部 Agent 或未来 Tauri Host 实现 `propose(...)` 与 `build(...)`。`propose` 接收 Context Pack v2：带角色的 `references[]`、冻结画布、当前选择和 revision。`build` 返回 `tosampool-agent-build/v2 / scene-draft`，包含完整 v4 Scene、`base`、`scope`、revision、摘要和预计变化。可选预览只能是小于 3MB 的安全图片数据。它由用户确认后才进入 Scene Mutation；不接受难以审阅的通用 JSON patch。
- 当前 Codex 可把该 Adapter 当作模拟桥接点：网页提交结构化事件 → 当前会话转交给隔离子 Agent → 宿主以同一 `requestId` 返回结构化答复。测试夹具使用过一次隔离子 Agent 的雪花球答复；这验证对话协议，不代表编辑器已经内嵌 API。
- 当前版本已具备临时 Scene 摘要、预计变化、基底/作用域、revision 冲突拦截、选择范围保持检查、应用与丢弃；“派生素材”还具备 `source` 参考、计划卡、透明候选预览与接受/丢弃，接受走既有 v4 撤销历史。尚未做固定时间候选组、API Key、模型对话、跨项目另存、可视化像素 diff 或最终的 Tauri Host；这些均属于下一层，而非 Runtime 职责。
